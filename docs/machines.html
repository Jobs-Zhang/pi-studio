PI STUDIO fleet

Connect trusted PI STUDIO runtimes when one machine is not enough.

Most PI STUDIO setups only need one runtime. When you do have more than one, machine federation lets the PI STUDIO instance you opened act as a gateway to other trusted runtimes while each machine keeps its own repositories, credentials, sessions, Pi package settings, and plugins.

What Fleet does

The local machine is available automatically. To reach another PI STUDIO runtime, register its base URL and, optionally, a bearer token.

After registration, the browser keeps talking to the current PI STUDIO origin. The gateway contacts the selected remote PI STUDIO server so you can work with its projects, workspaces, sessions, files, terminals, Pi packages, and compatible plugins.

Fleet shape 
Browser
  ↓
PI STUDIO gateway you opened
  ├─ [ Local runtime ]
  │
  ├─ [ Remote PI STUDIO runtime A ]
  │     ↓ selected machine
  │     projects, workspaces, sessions, terminals, Pi packages, plugins
  │
  └─ [ Remote PI STUDIO runtime B ]

When to use it

Federation is useful when you have more than one place where agents should work, but you want one stable browser entrypoint.

▦

Many dev boxes

Register a workstation, home server, cloud VM, or client-specific host without moving repositories.

⇄

One gateway

Open one trusted PI STUDIO URL and switch machines instead of juggling browser tabs and tunnels.

⌁

Local ownership

Each target machine keeps its own Pi auth, sessions, worktrees, terminal state, Pi package settings, and plugins.

Set up another runtime

Install and run PI STUDIO on every machine you want to register. The remote URL must be reachable from the gateway server, not just from your browser.

Install on each target 
$ npm install -g @pi-studio/pi-studio --allow-scripts=node-pty
$ pi-studio install
$ pi-studio doctor

Prefer a private path such as NetBird, Tailscale, WireGuard, private LAN, SSH tunnel, or an authenticated reverse proxy. If the remote is behind a path prefix, include that prefix in the machine URL, for example https://devbox.example.test/pi-studio. The machine registry normalizes the trailing slash; when opening that deployment directly in a browser, use its canonical https://devbox.example.test/pi-studio/ URL and configure the proxy to redirect the slashless form.

Do not expose PI STUDIO directly to the public internet. Register machines only over trusted network paths and only when you trust the endpoint.

Add a machine

  1. Open the PI STUDIO instance you want to use as the gateway.
  2. Open Actions → Add Machine.
  3. Enter the remote PI STUDIO base URL, including http:// or https://.
  4. Accept the suggested name or enter a friendlier sidebar label.
  5. Paste an optional bearer token if the remote endpoint requires one.

Use the machine selector beside the PI STUDIO brand (or the Machine chip on narrow layouts), then add projects, workspaces, and sessions on that machine. In an installed PWA, PI STUDIO also shows the gateway address so you can distinguish windows; see Which instance is this?.

Removing a remote machine only removes it from this gateway's registry. It does not stop the remote PI STUDIO service or delete projects, workspaces, sessions, or credentials on the target machine.

SSH machine connections

When the remote PI STUDIO is not directly reachable (a home lab box, a machine behind a firewall), add the machine with the SSH connection mode. The remote still runs PI STUDIO as usual; the gateway creates an ssh -N -L tunnel on demand and proxies HTTP and WebSocket traffic through it.

  1. In Actions → Add Machine, enter the remote PI STUDIO base URL as reachable from the SSH host — usually http://127.0.0.1:8505.
  2. Choose SSH — reach the URL through an SSH tunnel.
  3. Pick a host alias from your ~/.ssh/config (offered as autocomplete) or type one. Port, user, identity files, and jump hosts from that config apply automatically.
  4. Optionally set an explicit port, user, or identity file, or a password. Identity file and password are mutually exclusive; prefer keys.

Requirements and behavior:

  • An OpenSSH client (ssh) must be on the gateway's PATH; password auth needs OpenSSH 8.4+.
  • Host keys are accepted on first connect and verified afterwards (changed keys are rejected).
  • A password, like the machine bearer token, is stored in ~/.pi-studio/machines.json with owner-only file permissions. Prefer key-based auth when possible.
  • Tunnels start lazily, reconnect with a backoff window, and shut down with the gateway process.
  • The machine list shows an SSH badge and the tunnel state (up / connecting / failed) with the failure reason.

Which instance is this?

An installed PWA window has no browser URL bar or tab favicon, so PI STUDIO names the instance there itself: with several machines, the header dropdown lists every machine with its own brand icon and the local entry shows the gateway address; with only the local machine, a static bubble shows the instance favicon and the gateway address (host and any deployment path). On narrow layouts the breadcrumb leads with a Machine chip carrying the same icon and address. In a regular browser tab these location indicators stay hidden — the browser chrome already identifies the instance — and the machine control remains a pure selector.

The address is the ground truth for which gateway serves the window; the selected machine decides which runtime your projects, workspaces, and sessions live on.

Development deployments recolor the identity purple instead of the stock teal: the favicon, the PWA icons, and the installed PWA name, which becomes PI STUDIO (dev). Docker dev containers and source checkouts count as development deployments; package installs and Docker runtime deployments stay teal. Already-installed PWAs keep the icon and name captured at install time, so reinstall the PWA after a deployment changes flavor.

What works remotely

After you select a machine, the rest of the app works in that machine's scope. The gateway routes the selected-machine work to the target PI STUDIO runtime.

  • Projects and workspaces.
  • Files, previews, and Git status and diffs.
  • Pi sessions, transcripts, prompts, model controls, and commands.
  • Activity indicators and realtime updates.
  • Terminals and terminal command runs.
  • Pi package listing, install, remove, and update from Settings → Pi packages when supported by the target PI STUDIO runtime.
  • Compatible plugins installed on the selected machine.

Credentials stay on the target machine

Model-provider credentials, Pi configuration, Pi package-manager settings, plugin settings, OAuth state, repositories, workspaces, and sessions stay on the selected target machine. The gateway does not copy them into its own Pi configuration.

  • API-key model-provider configuration can be proxied through the gateway.
  • Subscription (OAuth) login and logout can be driven from the gateway while the machine is selected; the flow runs on the target machine and the credential is written there.
  • The optional machine bearer token is stored by the gateway and sent to the remote while proxying requests.

To sign in with a subscription, select the machine, open the login dialog, and choose Use a subscription. Because the provider flow runs on the target machine, its loopback redirect address (http://localhost:<port>/…) belongs to that machine, so the redirect page will not load in a browser running elsewhere.

  • When the dialog asks for a code or redirect URL, approve the login in the provider's page, copy the full URL from your browser's address bar, and paste it into the dialog. PI STUDIO shows that reminder exactly when a paste is expected.
  • When the provider offers a device-code option, choose it. Device-code logins need no paste: enter the displayed code on the provider's page.
  • A provider flow that offers neither a pasted response nor a device code cannot be completed from another machine. Cancel it, then either restart with the device-code option or log in on the target machine directly.

Use Actions → Open Selected Machine PI STUDIO when you need to authenticate directly on a remote machine or inspect it outside the gateway.

Plugins follow the selected machine

Machine-specific plugins come from the selected machine and operate on its workspaces. The gateway does not substitute its own backend when a remote plugin is unavailable or incompatible. Portable browser-only plugins can reuse a gateway copy; see the plugin guide.

Use Settings → PI STUDIO plugins to change the selected machine's plugin settings and check whether a restart is required. Browser-only changes need a gateway page reload. Server-backed changes require a restart of the target session daemon, then a page reload; restarting only the gateway web/API is not enough.

Upgrade the gateway and target together: mixed-version plugin operation is unsupported in either upgrade order. Remote plugins, including Git, may be unavailable or return 404. Restart the updated web/API processes and the target session daemon, then reload the gateway page. See plugin configuration and recovery for the rollout steps.

Run offline disable and safe-start commands directly on the affected target machine. A manual restart of its pi-studio-sessiond.service may interrupt active sessions and runtime ownership. For the native user service, run systemctl --user restart pi-studio-sessiond only after reviewing active work.

Browser and server plugins are trusted code, not isolated add-ons. Server plugins run with the target daemon's user permissions and can stall or crash its sessions and terminals. Only federate machines whose installed PI STUDIO plugin packages you trust.

Trust boundaries

Machine federation is for trusted users, trusted PI STUDIO servers, and trusted network paths. Adding a machine gives the gateway permission to contact that URL and forward user-initiated PI STUDIO traffic to it.

  • Use private networking, an SSH tunnel, or an authenticated reverse proxy.
  • Do not include credentials in the machine URL itself.
  • Use bearer tokens or proxy authentication when a remote endpoint needs an extra gate.
  • Treat browser and in-process server plugins installed on every federated target as trusted code.

Troubleshooting

Remote machine records are stored on the gateway in ~/.pi-studio/machines.json. If PI_STUDIO_DATA_DIR is set, they live under $PI_STUDIO_DATA_DIR/machines.json.

  • Use Actions → Refresh Selected Machine to re-check health.
  • Make sure the remote URL is reachable from the gateway server.
  • Open the remote PI STUDIO directly to verify it is running and to complete model-provider login flows.
  • For plugin lifecycle/peer compatibility errors, upgrade the gateway and target together, restart the updated web/API processes, manually restart the target session daemon, then reload the gateway page.
  • Check pi-studio logs on both gateway and target for proxy, plugin activation, health, conflict, or revision diagnostics.
  • Use the target's offline pi-studio plugins disable or safe-start commands when sessiond cannot start normally.
